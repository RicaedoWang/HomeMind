## 逐段讲稿

### 【01 封面】0:00

各位老师好，我是 **[你的名字]**。

我做的是一个智能家居的 Agent 中枢，叫 **HomeMind**。一句话概括它：**听得懂人话、记得住习惯、管得住风险**。

后面这三句，就是整个项目的骨架。

### 【02 痛点】0:15

先说为什么做这个。

我家那套所谓的"智能"家居，其实**只会听指令**。三个具体的麻烦：

第一，它**不记习惯**。我每天早上都得重新说一遍"空调调到 26 度"，所谓的智能退化成一台需要背诵指令的遥控器。

第二，它**分不清"现在做"和"到时候做"**。我说"提醒我九点关灯"，它**当场就把灯关了**。设备自己动了，这比什么都不做更难跟家里人解释。

第三，它**没有边界**，一个账号能操作所有人家的设备。

所以我后来的判断是：问题**不在模型不够聪明**，在于缺了执行前后的两层约束。

### 【03 三条规矩】0:50

我给自己定了三条死规矩：**听得懂人话**、**记得住习惯**、**管得住风险**。

前两条靠技术选型就能做到——规则引擎加大模型双模，任一层都能独立跑完；三层记忆，召回结果能反向改写工具参数。

第三条最难，也最贵。我把它单独拿出来讲。

### 【04 架构】1:10

【如果时间紧，这页一句话带过】

架构分六层。真正让它不像玩具的，是**工具层**——超时、重试、熔断、幂等，全部内建在注册中心里，业务代码只管干活。

好处很实在：答辩时我能指着代码告诉你策略写在哪一行、为什么是这个值。

### 【05 链路】1:25

这是一句话进来之后走的六步。

我想重点说**第三步**：护栏排在执行**之前**。就这一行的顺序，决定了会不会误操作。

另外第二步做了两件容易被忽略的事：一是把"**现在**"注入进去——大模型是没有系统时钟的；二是读这个家**真实的设备名**——你自己加的那台咖啡机，它才听得懂。

### 【06 多 Agent】1:50

系统里其实有**两张图**。一张是刚才那条单 Agent 主链路，另一张是 Supervisor 分派三个子 Agent。

Supervisor 只做决策、**不碰工具**；三个子 Agent 各有工具白名单，设备管家调不动日程。

有人会问，多 Agent 会不会削弱安全？**不会**。因为两张图**共用同一份执行原语**，护栏还是只有一个位置。

### 【08 护栏】2:10

这一页我认为是整个项目**最贵的一页**。四条机制：

高危工具强制二次确认；创建类一律回显确认；**说不清是哪台设备就反问**；跨家庭访问 403 且**零副作用**。

第三条我想多说一句。你说"打开灯"，而家里有两盏灯，它不会替你挑一台——它会回你："客厅灯、主卧灯都对得上，你指哪一台？"

**宁可说听不懂，也不要替用户按下开关。**

### 【10 可验证性】2:35

那我怎么证明它真的能跑？四层测试：**296** 条单测、**54** 条评测、**43** 项端到端、**32** 项前端冒烟。

这四层**不是重复劳动**。单测用依赖注入旁路掉了认证，所以 JWT 中间件、静态托管、跨账号切换，它一次都没跑过——只能靠端到端验收兜住。各抓不同的东西，缺一层就有盲区。

### 【11 三个坑】3:00

最后讲三个坑，每个都让我改了几百行。

第一，**模型不知道今天是几号**。prompt 里写着示例日期，它当成了"现在"，用户建"今日任务"，条目一落地就显示逾期 5 天。

第二，**工具报了成功，其实没动**。界面说"已打开客厅灯"，灯根本没变。顺着这条线还揪出一个更狠的：自建门锁做任务联动时，会**反向把门锁上**，全程零报错。

第三，**我的评测把自己家的数据删了**。跑一次评测，设备全没了。

这三个都不是"功能没做"，是"做了但错了，而且测试没抓到"。所以我后来立了条规矩：**修完一个 bug，必须补一条能复现它的用例，还要把修复改回去，确认那条用例真的会红**。

### 【12 / 13 收束】3:30

这些是我还没做好的：Redis 和 Milvus 跑的是降级实现，多轮对话还认不出"它"指的是哪台。

下一步先做两件事：把评测红线挂到 CI，把 Redis 真跑起来。

我的汇报到这里。**这个项目最大的收获不是这些功能，是学会了怎么证明它们真的能用。** 谢谢。

## 常见提问的答法（30 秒版本）

**Q：为什么不用现成的 Agent 框架（LangChain Agent / CrewAI）？**
> 工具重试、超时、熔断这些策略在框架内部，出问题时只能读源码猜。自建的注册中心里，这些是能指着代码讲的。框架我只取了 LangChain Core 的协议层。

**Q：多 Agent 是不是过度设计？**
> 三个子 Agent 的价值是**工具白名单**——设备管家拿不到日程工具。这比"提高效率"实在。另外它们共用执行原语，没有引入第二套治理。

**Q：Redis / Milvus 到底跑没跑？**
> 跑的是降级实现：Redis 走进程内存，语义检索走字符 bigram Jaccard。代码是完整的，换配置就能切真服务，但我不会说它"已接入"。

**Q：这东西能真接到家里设备吗？**
> 工具层是 MCP 风格 Schema，替换 handler 就能接厂商 SDK。我另外写了一份《真实硬件接入方案》，用 ESP32 + ESPHome + Home Assistant，但还没实做。

**Q：最大的技术难点是什么？**
> 不是让模型听懂，是**让它别乱动**。我踩的三个坑里有俩属于这类：报成功没执行、反向锁门。这些的共同点是"静默错误"——不报错、日志干净，只有用户会发现不对劲。

**Q：如果重做一遍，你会先做什么？**
> 先把隔离和测试的骨架搭好。我这次是做到一半才补的 end-to-end 验收，中间漏了好几处数据泄漏——包括我自己的真实设备库被评测清空过一次。
