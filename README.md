## 一、30 秒了解这个项目

一个面向智能家居场景的 Agent 服务：用户说一句自然语言，系统识别意图、规划任务、
调用 MCP 工具控制设备或创建日程，最后返回应答——全程带安全护栏和链路追踪。

```
用户输入
   ↓
recall_memory  记忆召回（语义 × 时效 × 重要度）—— 必须在最前，因为要影响后续参数
   ↓
parse_intent   意图识别 + 多意图拆分 + 时间解析
   ↓
safety_gate    安全护栏：高危动作拦截、创建类回显确认、低置信度澄清
   ↓            ├─ 可执行 → execute_tools
   ↓            └─ 待确认 → 挂起，回显给用户
execute_tools  MCP 工具调用（超时/重试/熔断/幂等/降级）
                 ↑ 记忆补全参数："把空调打开" + 记忆里的 26 度 → set_value 26
   ↓
respond        应答生成（含失败兜底话术 + 记忆应用说明）
   ↓
write_memory   记忆写入（把本轮对话里的偏好存下来）

全链路 traceId 贯穿，结构化 JSON 日志
```

### 记忆真的会改变行为（不是花架子）

```
你：我喜欢睡觉时空调26度        → 写入记忆 preference:空调温度
你：把空调打开                  → 用户没提温度
    [应用] 记忆「喜欢睡觉时空调26度」→ 参数改为 set_value 26度
    助手：已将客厅空调设置为26.0度（按你记下的偏好…）
你：我习惯空调开24度            → 同主题归一化 → 覆盖旧偏好（版本 v2）
你：把空调打开                  → 这次设成 24 度，行为跟着记忆变了
```

### 2.2 两个必踩的坑（已修，记一下原因）

**坑 1 · pip 源配错 → 所有包装不上**

报错长这样：`Could not find a version ... (from versions: none)`

检查：`pip config list`
配置文件在 `C:\Users\<你>\AppData\Roaming\pip\pip.ini`

```ini
[global]
index-url = https://pypi.tuna.tsinghua.edu.cn/simple   ← 正确
```

两个常见错误写法（都不通）：
- `https://mirrors.tuna.tsinghua.edu.cn/pypi/web/simple`（路径错误）
- `https://mirrors.tuna.tsinghua.edu.cn/simple`（域名不通）

**坑 2 · requirements.txt 里写中文注释 → pip 解析失败**

Windows 下 pip 用系统 locale（GBK）读 requirements 文件，
UTF-8 中文注释会让它把包名解析坏，报同样的 `from versions: none`。
所以本项目的 `requirements.txt` **刻意保持纯 ASCII**，注释用英文——别改成中文。

### 2.4 接真大模型（可选，三步）

默认跑的是**规则引擎**（正则+关键词），不联网、不花钱。
想让 Agent 真正"聪明"，接一个真模型：

```bash
# 1. 在项目根目录的 .env 里填 Key，并把 mock 关掉
HM_LLM_API_KEY=你的key
HM_USE_MOCK_LLM=false

# 2. 自检（确认 Key 有效、接口通、JSON 输出能被解析）
python scripts/check_llm.py

# 3. 跑真模型版链路
python scripts/demo_agent_memory.py
```

支持任何 OpenAI 兼容接口（DeepSeek / 通义 / OpenAI / 本地 vLLM），
换模型只改 `HM_LLM_BASE_URL` 和 `HM_LLM_MODEL`。

**模型挂了会怎样？** 自动降级——意图解析回退规则、应答生成回退模板。
用户拿到的是"笨一点但能用"的结果，不是一个 500 错误，服务永远在线。

**模型在链路里干什么？** 两件事：意图解析、应答润色。
注意应答**只做表达层润色**，执行结果是确定事实由工具给出，
不许模型自由发挥——否则它会编出"已经帮你关了窗"这种鬼话（幻觉）。

### 2.5 VSCode + Code Runner

用 VSCode **打开 `homemind` 目录本身**（不是上层目录），
`.vscode/settings.json` 已配好解释器与 Code Runner：

```json
"python.defaultInterpreterPath": "D:\\anaconda\\envs\\homemind\\python.exe",
"code-runner.executorMap": { "python": "D:\\anaconda\\envs\\homemind\\python.exe -u" }
```

注意：**Code Runner 无视 `defaultInterpreterPath`**，必须单独配 `executorMap`，
否则按 ▶ 会用 PATH 里的裸 python，直接报 `ModuleNotFoundError`。
改完 `Ctrl+Shift+P → Reload Window` 才生效。

启动 API 服务：

```bash
uvicorn homemind.api.main:app --reload --port 8000
# 打开 http://localhost:8000/docs 看接口文档
```

Docker 全套（含 Redis）：

```bash
docker compose up -d          # 最小：只起 redis + api

## 四、核心设计亮点

### 1. 工具调用治理内建在注册中心

超时、重试、熔断、幂等、降级全部集中在 `tools/registry.py`，
业务 handler 只管干活，不用每个工具重复写重试逻辑。

```python
result = await registry.call("create_reminder", args, idempotency_key=key)
# 返回的一定是 ToolResult，绝不让异常穿透到用户
```

### 2. 安全护栏是独立节点，不是散落的 if

`safety_gate` 是图里的一等公民节点，保证"误操作率 = 0"这条验收标准
**有唯一的实现位置可审计**，而不是在各处 if 里碰运气。

### 3. 时间解析用规则而非全交给大模型

大模型解析"下周三下午三点"的错误率足以让用户抓狂。
所以采用 **规则为主 + 大模型兜底 + 解析不出就强制澄清**，绝不静默猜测。

### 4. 一切都可降级

| 依赖 | 降级方案 |
|---|---|
| Redis 不可用 | 自动切进程内存 |
| 大模型不可用 | 自动回退规则解析 |
| 工具调用失败 | 重试 → 熔断 → 用户可理解的兜底话术 |
| 时间解析失败 | 强制澄清，不猜测 |

### 5. 记忆召回不是简单 topK，而是三项加权

```
score = 0.6 × 语义相似度 + 0.2 × 时效衰减 + 0.2 × 重要度
time_decay = exp(-λ × Δt)      λ 默认 0.01/天
```

纯语义相似会把"三年前随口一提"和"昨天刚说"排在一起；
时效衰减让新鲜记忆优先，重要度让关键偏好不被埋没。
每条召回结果都返回三项分解值，分数**可解释、可调试**。

### 6. 权限在召回阶段就过滤

不是召回完再过滤——那样敏感内容已经进了模型上下文，等于泄露。
`visible_role` 在语义检索时就拦截（L4 管理员 / L3 成人 / L2 儿童 / L1 访客）。

### 7. 健康检查说实话

`/health` 的 `memory_mode` 是**真探测**的结果，不是复述配置：
```json
{"status":"ok","memory_mode":"memory(redis_unavailable:TimeoutError)"}
```

## 五之二、V0.8 多 Agent 协同

```
START → recall_memory → parse_intent → supervisor → safety_gate
          ─┬─(有分派)→ execute_agents → respond → write_memory → END
           └─(无分派)→ respond → write_memory → END
```

三个子 Agent，各管一摊：

| Agent | 领域 | 工具白名单 |
|---|---|---|
| `device_agent` | 设备控制 | device_control / device_list / lock_control |
| `schedule_agent` | 日程提醒 | create_reminder / list_schedule |
| `knowledge_agent` | 知识问答 | 无（只回答，不碰设备） |

**四条设计原则（面试重点）**：

1. **Supervisor 只做决策，不碰工具。** 它干三件事：分派、冲突检测、并发编排。
   工具执行仍然统一在 `safety_gate` 之后——**多 Agent 的引入没有削弱安全**，
   护栏依旧只有唯一一处实现。
2. **最小权限。** 每个子 Agent 只能调用白名单内的工具。即使 Supervisor 分派错了，
   日程 Agent 也碰不到门锁。护栏挡"该不该做"，白名单挡"有没有资格做"。
3. **冲突在执行前拦。** "把客厅灯打开再关掉"两个操作单看都合法，合起来自相矛盾，
   执行了就是误操作。所以 `detect_conflicts()` 在 supervisor 阶段就把冲突任务挂起，
   转安全护栏要用户确认。
4. **失败隔离。** 子 Agent 的 `run()` 永不向外抛异常，崩了就转成 failed outcome，
   其他 Agent 照常返回结果，主链路不崩。

**治理逻辑只有一份**：主链路和子 Agent 共用 `agent/execution.py` 的执行原语
（增量解析、记忆补全、幂等键），避免出现"主链路有幂等、子 Agent 没有"这种裂缝。

演示：`python scripts/demo_multi_agent.py`，六段——单领域分派 / 多领域并发 /
知识问答 / 越权拦截 / 冲突检测 / 失败隔离。

## 五之三、评测体系（回答"你怎么保证改一个不坏一片"）

```bash
python scripts/run_eval.py                 # 跑全量（默认 mock，确定性、不烧 token）
python scripts/run_eval.py --save-baseline # 存为基线
python scripts/run_eval.py --real          # 真模型评测（结果不稳定，别当回归基线）
```

当前成绩（52 条用例）：

| 指标 | mock 模式 | 真模型（2026-10-19 实测） |
|---|---|---|
| 总通过率 | 52/52 = 100% | **52/52 = 100%** |
| 意图识别准确率 | 50/50 | 50/50 |
| 工具选择准确率 | 45/45 | 45/45 |
| Agent 分派准确率 | 6/6 | 6/6 |
| **安全红线** | **9/9** | **9/9（一票否决）** |

> 真模型那一列不是"顺手跑跑"。**2026-10-19 第一次跑 `--real`，第一条用例就直接
> traceback**（`chat_json` 签名缺 `max_tokens`），修完又暴露出 2 条判断问题。
> 这三条 mock 一条都抓不到。教训写在这里：**mock 全绿只能证明规则层没坏，
> 证明不了 LLM 那条路能跑通**——那条路上的代码在强制 mock 的测试里是死代码。

**四条设计原则**：

1. **红线一票否决。** 涉及误操作的用例任何一条失败，本次评测即判不合格，
   进程退出码非 0——可以直接挂 CI 卡住合入。安全不用平均分衡量，
   误操作率必须收敛到 0，不能是 0.98。
2. **可复现。** 每条用例跑之前重置 Mock 设备与日程。Mock 层是模块级全局字典，
   不重置的话前一条关了灯，后一条查到的就是"关"，结果根本没法复现。
3. **环境隔离。** 评测用独立的 `data/eval.db`，绝不碰用户的真实记忆库。
4. **区分已知缺口。** 隐式偏好（"我怕热"这类没有明确习惯句式的表达）当前抽不出来，
   标为 `known_gap` 单列：既不让它污染通过率，也不让它悄悄消失——
   **红线用例禁止标 known_gap**（代码里直接抛错，安全没有下不为例）。

**基线对比**能指名道姓说出哪条从通过变成了失败。实测：把
`has_device and has_action and not has_knowledge` 改回 `has_device and has_action`
（疑问词不再压过设备动作），评测立刻报出 `sec-08「空调怎么打开」` 红线失败、
退出码变 1——这正是"改一行崩一片"被拦下的样子。

## 五之五、多租户与安全隔离（V1.0）

**租户 = 家庭。** 深圳家（我 / 妈妈 / 爸爸）和青岛家（小明）是两套完全独立的数据，
连"客厅灯"都是两台不同的设备——只是恰好同名。

### 演示账号（密码统一 `demo1234`）

| 用户名 | 家庭 | 角色 | 城市 |
|---|---|---|---|
| `wo` | 深圳的家 | L4 管理员 | 深圳 |
| `mama` | 深圳的家 | L3 共同管理 | 深圳 |
| `baba` | 深圳的家 | L3 成员 | 深圳 |
| `xiaoming` | 青岛的家 | L4 管理员 | 青岛 |

登录深圳家再登录青岛家，能看到的是**两套设备、两套任务、两套场景、两套 AI 记忆**。

### `family_id` 怎么穿透的（面试重点）

```
token（JWT，含 family_id / member_id / role）
   ↓ current_user 依赖注入
FastAPI 接口 → 取资源前做家庭断言：不属于 → 403，且零副作用
   ↓
AgentState.family_id
   ↓ agent/execution.py 统一注入（治理只有这一处）
arguments["__family_id"]  ← 服务端权威值
   ↓
设备 handler / 记忆读写 / 短期记忆会话键
```

关键取舍：`__family_id` **不写在工具的 JSON Schema 里**，模型看不见也造不出来；
处理时也刻意不读不带下划线的同名参数。
否则用户一句"去把小明家的灯关了"，模型就可能真的传个 `family_id=family_qd` 执行掉——
**租户边界必须由服务端说了算，不能交给模型输出。**

### 三条验收标准（实测输出）

```
① 小明看不到深圳设备          → True（深圳 10 台 / 青岛 6 台，清单完全不同）
② 小明控制深圳空调            → 403 无权操作该设备，且该空调状态一点没变
③ 两家各存一条"空调温度"      → 同 key、不同值、谁也没覆盖谁
     family_qd | preference:空调温度 = 喜欢空调开20度
     family_sz | preference:空调温度 = 喜欢睡觉时空调26度
```

> 跨家庭访问返回的是 **403 而不是 404**：404 等于告诉对方"这个 id 存在但不属于你"，
> 是免费的资源枚举线索。

> **诚实说明**：登录时服务端确实记录了真实客户端 IP，但"深圳 / 青岛"这个城市字段
> 来自账号档案的 seed 数据，**没有做真实 GeoIP 定位**。面试照这个口径说，别吹成"按 IP 识别家庭"。

完整设计与逐步落地记录见《HomeMind_多用户与隔离实现方案.md》。

## 五之六、真实交互闭环（V1.1）

这一版解决的是"演示能看、真用就穿帮"的三类问题。三条都来自实际点开界面后的观感，
每条都配了能复现它的测试。

### 1. 消息中心：从写死文案改成真实事件流

**问题**：消息里是三条写死的种子文案（"洗衣机洗涤完成""入户门锁 18:20 开启"），
跟用户做过什么毫无关系。用户刚把灯关了，消息还在讲洗衣机——点开就穿帮。

**改法**：新增 `src/homemind/api/events.py` 作为消息中心的**唯一数据源**，
每一次真实操作落一条事件（设备开关 / 场景执行 / 任务完成·取消·恢复 / AI 建提醒 / 登录）。
两条硬约束：

- **只有真执行了才记**。被安全护栏拦下的操作（门锁未确认）不写事件——消息中心不放假消息。
- **按家庭隔离**。事件挂在 `family_id` 桶里，别家做的事一条都看不到。

事件里带真实操作人（取自 token，不是请求体）和时间戳，前端用 `relTime()` 算相对时间，
不再有写死的"12 分钟前"。

### 2. AI 创建的提醒进今日任务框

**问题**：跟 AI 说"提醒我晚上九点关灯"，AI 回了"已创建"，今日任务框里**什么都不出现**。
根因是两套存储：家务任务在 `console._TASKS`，AI 提醒在 `calendar_server._SCHEDULES`。

**改法**：在展示层合并（`/state` 返回 提醒转成的任务卡 + 家务任务），
不硬合成一张表——两者生命周期不同（家务有设备联动、提醒没有），合表只会互相污染。
转出来的卡带 `isSchedule: True`、`source: "ai"`，前端据此显示"AI 创建"。

顺带补上提醒的完整生命周期：完成 / 取消 / **恢复** / **删除**。
其中"恢复"曾经直接 404（`reopen_task` 只认家务任务），
"删除"压根没有接口——能加不能删的提醒会永久挂在今日任务框里。

### 3. 所有渲染出来的元素，点下去都得有真实动作

新增两类验证，因为"渲染出来了"和"点了有反应"是两件事：

- **前端无头冒烟**（`scripts/smoke_web.js`，jsdom）：29 项交互逐个点，
  要落库的动作断言"发了请求"，纯界面动作断言"界面真的变了"。**点了没发请求就算失败。**
- **端到端验收**（`scripts/verify_interactions.py`）：真起服务 + 真实 JWT，28 项全过。

这轮补上的可点元素（原来都是死的）：

| 元素 | 点下去发生什么 |
|---|---|
| 设备卡整卡 | 切换开关（原来只有右上角小开关能点，手机上很难瞄） |
| 房间标题「N / M 开启」 | 整屋一键开关，**高危设备（门锁）跳过并在提示里说明** |
| 任务页任务行 | 待办 → 标记完成；已完成/已取消 → 恢复 |
| 「我的」页家庭成员 | 跳任务页并只看 TA 被指派的任务 |
| 「我的」页提醒条目 | 确认弹层 → 真删除 |
| 右栏用电「今日/本周/本月」 | 切换摘要条视图并滚动定位 |
| 右栏 / 「我的」页习惯条目 | 确认弹层 → 让 AI 忘掉（长期记忆 + 语义索引双清） |

### 4.（重要）顺手抓到的意图识别 bug

端到端验收跑出来的：`rule parsed 1 intent(s) ... types: ["device_control"]`。

> 对 AI 说 **"提醒我晚上九点关灯"**，它没建提醒，**当场把客厅灯关了**。

根因在 `agent/intent.py` 的 `_classify`：设备分支（`has_device and has_action`）
排在提醒分支（`has_schedule`）前面，这句话里既有"灯"（设备）又有"关"（动作），
于是在设备分支就被判走并执行了。

改法是把**提醒判定提到设备判定之前**，并在 LLM prompt 里补上同样的裁决说明
（规则词表和模型 prompt 必须两边同步，否则会出现"规则好用、模型翻车"的分裂）。
依据就是项目自己定的那条原则——**误执行比漏执行严重得多**：
设备动了是看得见的错误，漏了最多是没反应。没有时间时走 `needs_clarify` 反问几点，
宁可多问一句，也不替用户动设备。

修完 `pytest -q` 103 全过、端到端评测 52/52 **无回退用例**；
并且照项目惯例做了反向验证——**把修复改回去，新用例当场把它抓住**（红线 8/9、评测判不合格、退出码非 0）。

pointerup   → 左滑：位移 > 72px 才算取消意图，否则回弹（防误触）
              上滑：位移 > 56px 折叠任务中心
              点击：位移 < 10px 且时长 < 500ms → 完成任务
```

## 五之八、注册与场景自定义（V1.2）

### 为什么加这两个

在此之前，"家庭"和"场景"都是**代码里的常量**。演示好用，但意味着：
新用户不存在，新场景也建不出来。一个智能家居产品连注册都没有，
面试官第一句就会问"那你这套多租户是给谁用的？"

### 注册：两种模式，一条真实路径

| 模式 | 角色 | 结果 |
|---|---|---|
| 创建新家 | **L4 户主** | 生成家庭 → 初始化 10 台设备 → 写入默认场景 |
| 邀请码加入 | **L3 成员** | 同一个家、共享设备、成员编号递增（member_002…） |

```bash
POST /api/auth/register        # mode=create / join，成功即发 token
GET  /api/auth/family/invite   # 只有户主能看（L3 → 403）
```

四个刻意的决定：

1. **注册成功直接发 token**，不让用户"注册完再登录一次"，那一步纯属折磨。
2. **重名返回 409 而不是 400**：这是唯一"换个用户名就能成"的错误，
   前端据此把光标停回用户名框，而不是弹一句通用失败。
3. **先查重名再建家庭**。反过来一旦撞名，库里就留下一个没有任何成员的"空家"，
   而且没有任何入口能删掉它——不可回收的垃圾数据。
4. **新家必须有设备**。注册完给个空控制台，用户会以为自己点错了。

### 场景自定义：内置只读，自建全 CRUD

```bash
GET    /api/console/scenes           # 内置 + 自建，带 builtin / editable 标记
POST   /api/console/scenes           # 新建（名字 / 图标 / 动作列表）
PUT    /api/console/scenes/{id}      # 改名、改动作（内置 → 403）
DELETE /api/console/scenes/{id}      # 删除（内置 → 403）
```

存储分两层：
- **内置场景在代码里**（`BUILTIN_SCENES`）——跟代码版本走，改代码即生效
- **自建场景在 SQLite**（`data/homemind_content.db`）——跟着用户走，重启不丢

两个关键约束：

- **每个动作里的设备都要按本家庭校验**。场景是"一次动好几台设备"的批量操作，
  只信前端传来的 `device_id` 就等于开了后门：单设备接口 403，
  场景接口却能把别家的地暖打开。这条有专门的用例守着。
- **内置场景不给改不给删**。它是演示与回归测试的基线，
  让用户改坏"回家"模式，第二天所有文档和截图全对不上。

| 项 | 结果 |
|---|---|
| 单元测试 | **133 passed**（新增 26 条：注册 14 + 场景 12） |
| 端到端验收 | **28/28**（新增 14 项：注册、邀请码、场景增删改、越权拒止） |

## 五之九、登录页重构：一屏只留一个动作（V1.2.1）

### 改之前是什么样

四个账号平铺成四行、底下挂一张账密表单、再挂一张填了一半的注册表单，
一屏三个入口互相打架。站在门口的人第一眼不知道点哪儿——
**"能点的地方太多"和"没有能点的地方"一样糟糕**。

### 改完之后

```
        ✦ HomeMind
   智能家居控制台 · 每个家庭的数据完全隔离

   ┌─────────────────────────┐
   │          我             │   ← 上次登录的身份
   │    深圳的家 · L4 · 深圳   │
   │       切换账号 ⌄         │   ← 展开：最近登录 + 其他演示账号
   │                         │
   │      [  一键登录  ]      │   ← 唯一的默认动作
   └─────────────────────────┘

    👤        ➕        💬
  账密登录   注册账号    帮助
```

三条路各有归属：
- **一键登录**：上次那个人，直接进。内置演示账号密码公开（`demo1234`）所以能一键；
  **自己注册的账号没有公开密码**，点它就会退到账密面板并预填用户名——不假装能进。
- **切换账号**：下拉展开，分「最近登录」和「其他演示账号」两组，最多记 5 个身份。
  记录存在浏览器 `localStorage`，只存昵称/家庭/角色这类展示信息，**不存密码**。
- **注册账号**：弹出面板，**先让人选"创建新家庭"还是"加入已有家庭"，再给对应表单**。
  以前默认选中"创建新家"，想在错的表单里填对的字段，是必然结果。

### 三个刻意的决定

| 决定 | 为什么 |
|---|---|
| 登录页不再平铺账号 | 默认动作只能有一个。其余是次选，压到底部做成小图标 |
| 注册先选路再填表 | 两条路要填的字段不是一套（家庭名+城市 vs 邀请码），混在一屏必然填错 |
| 登录记录只存展示信息 | 存密码等于把别人的密码明文写进浏览器；token 失效就重输一次，代价远小于泄露 |

### 踩到的坑：函数名撞车，静默失效

登录页的弹出面板本来叫 `openSheet()` / `closeSheet()`——**AI 对话面板早就有这两个同名函数**。
JS 的函数声明提升不看定义顺序，后定义的覆盖先定义的，于是：

- 点"注册账号" → 实际执行的是 AI 面板的 `openSheet()` → **登录面板纹丝不动**
- 全程没有一行报错，jsdom 也没捕获到异常

冒烟脚本抓出来的方式很朴素：断言"点完 `#login-sheet` 必须不再是 hidden"，它还是 hidden。
**改名的成本是 9 行，猜的成本是半小时**。教训已写进踩坑记录。

## 六、关键踩坑记录

**"审批超时"不等于"请求没发出去"。**
加注册功能时用 curl 打了一次建家接口，工具返回的是"审批超时，内容已拦截"，
看上去那行命令没执行。半小时后查库发现：账号 `testnew` 和「苏州的家」
**已经写进真实账号表了**——请求早就打到服务，只是回执没回来。
教训：**任何写操作都要先假定它会成功**，把数据隔离做在动作之前，
而不是等看到报错再去收拾。

**新增一个可写的存储，就必须同时给 conftest 加隔离。**
家庭库和场景库一旦用默认路径，跑一次 pytest 就会往 `data/` 里写一堆测试家庭。
`tests/conftest.py` 现在有 `_isolated_content_store`，自动把两个库换成 `tmp_path`；
`verify_interactions.py` 也在起服务前调 `isolate_stores()`。
**"测试不碰真实数据"不是纪律，是配置。**

**单设备接口有租户校验，不等于批量接口也有。**
场景是"一次动多台设备"的批量操作。如果只校验场景属于本家庭、不校验里面
每个 `device_id`，用户就能拿一个自己家的场景去改别人家的设备。
批量接口是越权最常漏的那条缝，必须逐个校验。

**用元组解包遍历结构，字段一多就崩。**
场景动作原来是 `(device_id, action, value)` 三元组，
`for device_id, action, value in scene["actions"]` 这种写法，
一旦要加个"延时"字段就全线报错，而且从 JSON 读回来的自建场景天生是 dict。
现在统一成 dict，多一个字段不影响任何调用方。

**同名函数被后定义的那个静默覆盖。**
`web/assets/app.js` 里 AI 对话面板早就有 `openSheet()` / `closeSheet()`，
V1.2.1 的登录页弹出面板又用了同样两个名字。函数声明提升不看书写顺序，后定义的赢——
于是点「注册账号」实际执行的是 AI 面板的逻辑，**登录面板纹丝不动，控制台一行报错都没有**。
这类 bug 没有堆栈、没有日志，只能靠"点完必须断言界面真的变了"抓出来；
如果冒烟只断言"没抛异常"，它会一路绿到上线。**加交互前先 grep 一遍函数名。**

**mock 模式下的绿，证明不了真模型能跑。**
2026-10-19 第一次跑 `run_eval.py --real`，第一条用例就 traceback：
`TypeError: LLMClient.chat_json() got an unexpected keyword argument 'max_tokens'`。
当时 105 条单测、52 条 mock 评测、22 项前端冒烟全绿，一条都没抓到——
因为 `if not client.enabled: return` 在强制 mock 时提前返回，出错那行是**死代码**。
**凡是在「真模型分支」后面的代码，都必须有一条显式构造 enabled 客户端的用例**，
否则它永远不被执行，也就永远不知道自己是不是坏的。

**假客户端不能自己重写签名。**
修上面那条时，回归用例的假客户端若自己写一个 `chat_json(..., max_tokens=80)`，
测的就是假签名——调用方传错参数照样"通过"。正确做法：把真实的
`LLMClient.chat_json` 绑到假对象上，只替换网络层 `chat`。另注意
`parse_json` 是静态方法，裸赋值成类属性会退化成普通函数（self 被一起传进去），
要用 `staticmethod()` 包一层。

**评测断言在考模型文笔。**
断言要"客厅灯"，真模型答"客厅的灯已经关好了"——工具、意图、分派全对，多一个"的"就判失败。
这不是系统故障，是断言太脆。比较前剥掉连接词与标点即可；只剥连接词，
房间名/设备名仍须原样出现，所以"把卧室灯关掉"这种真错照样抓得住。

**LLM prompt 的意图边界不写清，模型就会自己发明。**
"查看我的日程"被判成 memory_query，因为 prompt 只写了"想查看 Agent 记住了什么 →
memory_query"，而这句话也带个"我的"。规则层有"日程"这个词能兜住，但真模型模式优先走
LLM，规则结果不参与。**每加一个意图，prompt 与规则词表都要两边同步**——
这条早就写在原则里，仍然漏了一次。

**LangGraph 不能用 lambda 包 async 节点。**
```python
# ❌ 错误：LangGraph 用 inspect.iscoroutinefunction 判断，lambda 会被当成同步节点
graph.add_node("parse", lambda s: parse_intent_node(s, parser))
# 报错：InvalidUpdateError: Expected dict, got <coroutine object>

# ✅ 正确：用 async def 闭包
async def _parse(state): return await parse_intent_node(state, parser)
graph.add_node("parse", _parse)
```

**门锁必须走专门的高危工具。**
如果把门锁当普通设备开关，安全护栏里的 `HIGH_RISK_TOOLS` 就永远命中不了——
护栏形同虚设。这个 bug 是靠实际跑一遍才暴露的。

**多意图不能因为一个任务待确认就全卡住。**
"关灯 + 建日程"里，关灯应该马上做，日程才需要确认。

**Gradio 6 砍掉了 Chatbot 的老数据格式。**
旧写法 `history.append([用户话, 助手话])`（二元组）在 Gradio 6 直接失效——
新版只接受 messages 格式 `[{"role": "user", "content": ...}]`，
且 `bubble_full_width` 参数也被移除（`TypeError: unexpected keyword argument`）。
装依赖时没锁定大版本，踩到就得改代码：

```python
# ❌ Gradio 4/5 的写法，6.x 报错
history = history + [[message, answer]]
chatbot = gr.Chatbot(height=430, bubble_full_width=False)

# ✅ Gradio 6
history = history + [{"role": "user", "content": message},
                     {"role": "assistant", "content": answer}]
chatbot = gr.Chatbot(height=430)
```

教训：**UI 库的大版本升级不看 changelog 就上，等于给自己埋雷。**
requirements 里虽然写了 `gradio>=6.0.0`，但代码是按 API 写的——升级后必须跑冒烟，
静态检查看不出组件参数被删了。

**意图规则表的判定顺序 = 误执行风险。**
"提醒我晚上九点关灯"被判成 `device_control`，Agent 当场把灯关了——
句子里既有"灯"（设备）又有"关"（动作），撞上排在前面的设备分支。
设备分支和提醒分支谁在前面，不是代码风格问题，是**会不会误动用户设备**的问题。
判错了宁可漏（反问一句），不能错执行。详见 [五之六、真实交互闭环](#五之六真实交互闭环v11)。

**消息中心写种子文案，是最容易骗过自己的假数据。**
三条形似真实的操作记录，代码跑得通、测试也能过，
但用户点开一看"我刚关了灯，你这还在说洗衣机"就穿帮了。
判断标准很简单：**这条数据能不能被用户的操作改变？** 不能，它就是假的。

**任务页点完成没反应，因为 DOM 依赖放错了层。**
`completeTask()` 开头写的是 `const card = $(...); if (!card) return;`——
找不到卡片就直接返回。首页有卡片能跑，任务页没卡片就永远静默失败。
"某段逻辑在另一个页面也能用"这种事，不点一遍是发现不了的。

**测试文件互相蹭 sys.path。**
`test_eval.py` / `test_multi_agent.py` 没自己写 `sys.path.insert`，
靠同批次其他测试文件插进去的路径才能 import `homemind`——
所以`pytest`（全量）没事，单独跑某一个文件就 `ModuleNotFoundError`。
路径是全局的事，应该在 `pytest.ini` 里用 `pythonpath = src` 解决，不是靠跑批顺序。

**端口上挂着的可能是上一场的旧进程。**
`console_server.py` 端口被占会自动顺延（8010 → 8011），但"给别人的链接"不会跟着改——
旧进程还在 8010 上跑着**改 bug 之前的代码**，浏览器连过去测的全是旧逻辑，
新代码明明修好了却"看起来没修"。教训：**报端口之前先 `netstat -ano` 确认，
长期演示前先杀干净旧实例**（设备状态是进程内字典，多实例还不共享状态）。

**跑图复现必须换临时记忆库。**
复现"说习惯"类 bug 时直接 `ainvoke` 整张图，`write_memory_node` 会把测试语句
当成用户的真习惯写进 `data/homemind.db`——复现一轮污染一条。
复现脚本必须 `set_memory_service(MemoryService(long_term=LongTermMemory(db_path=临时)))`，
或者跑完用 `forget_by_keyword` 清理。

**Python 的条件表达式是右结合的，跨行写三元一定要加括号。**

```python
# ❌ 少一对括号，解析成 "unlock" if turn_on else ("lock" if is_lock else action)
"action": "unlock" if req.action == "turn_on" else "lock"
if device.device_type == "lock" else req.action,

# ✅ 先判"是不是门锁"，再判开还是关
"action": ("unlock" if req.action == "turn_on" else "lock")
if device.device_type == "lock" else req.action,
```

后果很实在：**任何设备**的 `turn_on` 都被翻译成门锁的 `unlock`，
工具回"不支持的动作"，于是灯 / 空调 / 窗帘**永远打不开**，
而 `turn_off` 原样透传还能用——表现成"能关不能开"。
用户点了一下午开关才发现。这类 bug 静态检查不报、类型检查不报，
只有真点一遍才暴露。

**"工具被调用"不等于"操作生效"。**
`device_control` 遇到不支持的动作返回 `success=False`，但调用本身没抛错，
注册中心的 `result.ok` 仍是 `True`。只判 `result.ok` 的下场是：
API 回成功、消息中心还记一条"打开了客厅灯"——灯根本没动。
凡是要落事件 / 回执的地方，都得看工具自己报的 `success`。

## 五之十、大模型没有时钟，也没有"这件事做完了"的直觉（V1.2.2）

2026-10-20 实测报上来两个 bug，看着是两件事，根子是一个：
**当前时间从来没注入给大模型。**

**现象一**：问「现在是什么时间」，助手答「我这边看不到当前时间，没法准确告诉你」。
**现象二**：「创建今日任务：晚上七点去遛狗」，回显成了
`即将创建：去遛狗（2026-10-14T19:00:00）`——比当时早 6 天。
用户点了确认，任务真建出来，列表立刻显示「逾期 5 天 18 小时」，
标题还挂着「今日任务 · 有逾期」。今日创建的任务，逾期了。

根因在意图解析的 prompt 里躺着：

```
scheduled_at: ISO8601 时间字符串（如 2026-10-14T09:00:00）
```

模型不知道今天几号，看到这个"示例"，就把它当成了现在。
用户说"今日"，它认真地把"今日"算成了示例里那个日期。
**写死的示例日期是模板里最脏的一种坑：它对人是举例，对模型是事实。**

修法三层：
1. 两条 prompt（意图解析、应答生成）开头统一注入 `describe_now()` ——
   「现在是 2026年10月20日 星期二 13:06」。星期必须给：
   "下周一""这周五"全靠它推算，让模型自己数日子就是多送一次出错机会。
2. 示例日期删掉，换成"必须用上面那行『现在』推算" + 相对例子。
3. 规则模式（无模型）在应答节点加一句模板兜底，
   否则问时间会得到"我在听。可以说「我喜欢…」"。

**为什么 133 条单测 + 52 条评测全绿也没抓到**：
规则解析路径走的是 `datetime.now()`，日期本来就对；
出问题的只有 LLM 分支，而测试强制 mock，LLM 分支压根不执行。
新加的用例不去断言"模型答得对不对"（花钱且不确定），
而是**把 prompt 抓下来断言**：必须含今天的日期，**必须不含 `2026-10-14`**。
后者是硬约束：谁再往 prompt 里塞写死的示例，这条用例立刻红。

**顺带挖出来的第三个问题：手打「确认」等于什么都没做，还会被告知"已创建"。**
回显文案写的是「确认请回复「确认」」，用户就真的回一个"确认"。
但"确认"两个字单独进来被判成聊天，`tasks` 为空，执行层无事可做；
应答层翻到历史里那句"即将创建：去遛狗"，张口就编"任务已创建"。
而前端点「确认执行」按钮走的是**重发原句 + `confirmed=true`**——
所以**按钮能用、手打不能**。端到端验收 28/28 全过，因为它测的正是按钮那条路。
等于提示文案在引导用户走进唯一走不通的那条路。

修法：后端存一份"待确认原文"，认出纯确认词就把它重放一遍，
让手打与点按钮合并成同一条执行路径。判定收得很窄（"确认一下明天的天气"
不算确认），执行完立刻清掉——否则用户十分钟后随口一句"好"，
十分钟前那句操作会突然补执行，这是最经典的"设备自己动了"。
同时 prompt 里加硬约束：**"即将创建…"只是询问确认，什么都没执行**，
只有"刚刚实际执行的结果"里列出的才算完成，不许因为历史提过就宣称已完成。

> 这两条合起来的教训是：
> **凡是模型"应该知道但没被告知"的事实，都会变成幻觉的原料。**
> 时间、身份、家庭、权限——项目里每一个已经按服务端权威值注入的，
> 都别再让模型自己猜。

## 七、面试怎么讲

> 我用 LangGraph 搭了一个智能家居 Agent 中枢，链路是
> 意图识别 → 安全护栏 → 工具执行 → 应答生成四个节点。
> 工具层用 MCP 协议标准化，注册中心内建了超时、重试、熔断和幂等治理。
> 安全护栏做成了独立节点，高危动作和创建类操作强制二次确认，保证误操作率为零。
> 时间解析我用规则为主、大模型兜底、解析不出来就强制澄清——
> 因为时间解析错误是这类产品最容易被投诉的点。
> 全链路 traceId 贯穿，依赖全部可降级：Redis 挂了走内存，模型挂了走规则。

**能被追问的点（都已在代码里落地）：**
1. 熔断怎么实现的？（连续失败 N 次开闸，30 秒后半开试探）
2. 幂等怎么保证？（写操作生成幂等键，命中缓存直接返回上次结果）
3. 增量调节"调低两度"怎么处理？（先 query 当前值，再算目标值 set_value）
4. 部分执行怎么做的？（安全网关按任务粒度判定，可执行的先跑）
